# 邻课产品体验评审与改进建议

评审日期：2026-11-11。对象：本地运行站点 `http://localhost:8180/` 及当前工作区实现。第1—8节保留改动前的评审，第9节记录用户授权后的实施与验证。本文不替代已确认的[首版规则](../mvp-spec.md)。

## 1. 总体判断

**视觉方向可以保留，核心业务已有基础，但还不够顺手。下一轮应优先改善“找到合适对象并开始联系”的路径。**

绿色、米白背景、白色卡片和留白形成了统一、安静的视觉风格，适合本地老师与学习需求的匹配场景。老师卡片已经突出教学方向和报价；需求有年级、科目、地点、预算，详情也包含目标、时间、频率。没有必要为追求新鲜感推翻整个设计。

主要问题集中在四处：新访客难以快速看懂双向入口；筛选和比较效率偏低；登录、刷新会打断正在进行的寻找；“投递、邀请、互选、授权”的表达与用户期待的“联系沟通”之间存在距离。

这是一款双向撮合平台：需求方找老师，老师找合适的需求，双方表达兴趣后沟通后续安排。当前的“需求”尚不是已成交订单，“互选”也不等于预约或合作成功，页面应保持这种区分。

## 3. 优先问题与改进方案

P1：影响理解、寻找或联系，应在下一轮优先处理。P2：提高效率和一致性，可随后完善。本次没有发现并确认需要标为 P0 的阻断问题；这不构成完整质量或安全验收。

### P1-01：首页没有清楚呈现两类用户的入口

**现状／实测：** 首页主体为登录表单和品牌口号，匿名导航仅有“浏览需求”；“发现老师”只有需求方登录后才出现。用户希望找老师时，首页没有对应的明确动作。

**影响：** 首屏更像账户系统，新访客需要自行猜测“我应该从哪里开始”。

**建议：** 保留品牌风格，增加明确的价值说明：“在坪山找合适的老师，也让老师找到合适的教学需求。”设置“我想找老师”“我是老师，找需求”两个入口，并用一句话说明“选择合适对象 → 表达意向 → 双方同意交换联系方式”。登录保留为必要动作的前置步骤。

**规则边界：** 现有规则只允许已登录需求方查看老师资料。首页可以展示找老师的入口和流程说明，点击后登录并回到老师发现；不能顺便向匿名访客开放老师资料，也不能默认替用户选择业务身份。

**验收：** 新访客无需阅读长说明，就能指出自己应点哪个入口、联系后会发生什么。

### P1-02：登录打断原需求，已有用户也落到资料页

**现状／实测：** 从需求详情点击“登录后以老师身份投递”，URL 中的 `request` 参数被清除。使用已公开资料的合成老师登录后，进入老师资料编辑页，没有回到原需求。需求方普通登录后同样进入资料页。

**代码依据：** `AccountApp.vue` 的 `showLogin()` 调用 `clearPublicUrl()`；`loadAccount()` 对已有业务身份设置 `screen = 'profile'`。

**建议：** 保存站内的返回目标和动作上下文，例如需求 ID、原筛选条件；登录成功后先验证身份和对象当前有效性，再恢复原详情。资料完善或公开要求只在需要时引导，完成后仍可返回原对象。没有返回目标时，需求方优先进入老师发现或待回应事项，老师优先进入需求列表或待回应事项。

**验收：** 已完善资料的老师从需求 A 发起登录后返回 A；未完善资料时显示具体缺项；需求已到期、身份不符或无权限时给出可执行的替代入口，不静默丢失目标。恢复页面不能自动发送意向。

### P1-03：页面与筛选状态不能可靠恢复

**现状／实测：** 公开列表选择“绘画”并筛选，能正常得到绘画需求；URL 仍为 `/`。刷新后回到登录首页，筛选上下文丢失。单个需求详情的 `?request=...` 刷新可以恢复，这是已有的正向能力。

**代码确认：** 老师详情、撮合详情主要保存在组件状态；需求详情通过 `replaceState` 改写 URL。没有形成统一、可恢复的页面导航机制。

**建议：** 为列表、详情和撮合页建立一致的站内路由；类别、方式等可公开的筛选条件放入查询参数。返回列表时恢复筛选、分页位置及合理的滚动位置。详情与列表之间形成浏览器历史记录，前进/后退与页面返回按钮行为一致。私有联系方式和凭据不进入 URL。

**验收：** 筛选→详情→返回仍保持原列表；刷新仍在当前页面；失效分页游标有明确回退；私有详情刷新仍重新校验当前账号权限。

### P1-04：移动端首屏大部分用于筛选，核心内容太靠后

**现状／实测：** 在 390×844 的需求列表中，第一张卡片顶部约在页面 y=748px，首屏无法完整看到预算和查看按钮。老师列表的三个筛选项在手机上纵向展开，同样挤压首屏。桌面需求列表在 1000px 高度内也基本只显示一张完整卡片。

**建议：** 缩短导航与页标题之间的留白；把类别、方式等常用条件做成紧凑控件，其他条件放到“更多筛选”。当前只有一个开放行政区时，将“坪山区”作为范围说明，减少无效选择。移动端收起筛选后展示已选条件和清空入口。

**验收目标：** 390×844 默认列表首屏至少能看清第一条对象的名称、类别/方向、报价和详情入口；展开筛选不遮挡提交/关闭按钮，无横向溢出。目标应在实际页面验证后调整，不能靠把字体压小达成。

### P1-05：列表还不足以支持快速判断“是否合适”

**现状／实测与代码确认：** 需求卡片有标题、类别、区域/地点、方式、年级/科目、预算和发布者，但没有时间、频率及单次时长。老师卡片已有教学方向和突出报价，但没有可服务时间。相关信息在现有详情字段中已存在。

**建议：** 需求卡片增加一行时间摘要，如“周末下午 · 每周1次 · 每次1.5小时”；老师卡片增加“可服务时间”摘要，未填写时保持“时间可协商”。时间摘要过长时截断并可在详情完整读取。预算突出显示，发布者等辅助信息降为次级。线上需求优先显示“线上”，地点作为补充，避免一行中重复出现“坪山区”。

**范围控制：** 先复用已有字段和格式化逻辑，不为这轮卡片改造新增排课表、资格认证、评分或复杂推荐系统。不把自由文本推断为精确可预约时间。

**验收：** 双方在列表即可比较方向、方式、地点、价格和时间，不必逐个打开详情；卡片摘要与详情一致。

### P1-06：“联系”的结果和下一步不够直观

**现状／实测：** 老师详情动作是“选择需求邀请”；需求详情的匿名动作是“登录后以老师身份投递”。邀请准备页先展示“反向发起不会自动互选”等规则，再让用户选择需求。

**代码确认：** 双方要先投递/邀请并接受，之后各自选择手机号或微信并授权；授权双方有效才展示联系方式。当前没有站内聊天。

**建议：** 先明确说明“发起意向，对方接受后可申请交换联系方式”。动作可用“邀请这位老师”“我对这个需求感兴趣”；不能只改成“立即聊天”而不提供聊天。互选成功后，用显眼的“下一步：交换联系方式”引导，并将步骤表达为“发送意向 → 对方回应 → 双方同意交换联系方式”。

复杂边界在相关状态出现时解释：已有意向则“你们已有联系记录，查看进度”；对方尚未回应则“等待对方回应”；联系方式尚未填写则提供就近补充入口。保留逐项选择、明确同意、撤回和变更重确认，不用默认勾选来缩短流程。

**验收：** 用户在发起前知道这不会立即发消息或暴露联系方式；接受后知道接下来由谁做什么；未获授权不出现对方联系方式。完整双账号验证属于后续实施验收。

### P1-07：待回应事项缺少显著入口，授权操作位置偏后

**现状／代码确认：** 导航“撮合进度”没有待回应数量；进度列表按“待回应/已互选”等筛选，未将“等我回应”和“等对方回应”分组。详情先展示完整需求与老师资料，后面才放接受/拒绝及联系方式授权。

**影响判断：** 用户可能漏掉需要自己处理的事情；长内容下方的下一步操作不容易被发现。当前合成账号的撮合列表为空，因此本轮没有实测有待办时的真实发现率。

**建议：** 增加“需要我处理”的入口或计数；详情顶部显示对象、当前状态、下一步和动作锚点，原始资料保留在下方供核对。互选后将交换联系方式的状态放在显眼位置。先做必要的站内状态提示，不要求扩展完整通知中心。

**验收：** 用两个合成账号覆盖待我回应、等对方回应、需本人授权、等对方授权、已可联系五种状态，均能在详情首屏找到下一步；计数来自服务端真实状态。

## 5. “联系后沟通”的产品选择

用户已明确双向选择与联系的目标，但本轮描述没有明确要求站内实时聊天。下面两种方案对应不同范围，不能混为一谈。

| 方案 | 用户体验 | 与当前实现的关系 |
| --- | --- | --- |
| 首版继续采用意向＋双方交换联系方式 | 表达兴趣，对方接受，双方同意后用微信/电话商量后续 | 与已确认规格一致。建议先把入口、状态和文案做好；无需为了这次评审重写撮合逻辑 |
| 增加站内沟通 | 从老师或需求详情进入会话，在站内讨论，再自愿交换联系方式 | 属于新的产品范围，需要会话关联、历史消息、未读、发送失败、屏蔽/举报等设计，不能只新增聊天按钮 |

另外，当前需求方必须拥有有效公开需求才能邀请老师；尚未发布需求的人不能直接询问老师。**这是现有规则带来的联系门槛，不是按钮故障。** 近期可把“先发布需求”的原因和返回路径说明清楚；若目标是“先咨询老师，再决定发布需求”，应单独确认是否引入咨询流程。本次不擅自修改已确认规则。

## 6. 建议的页面组织

| 页面 | 主要内容 | 主要动作 |
| --- | --- | --- |
| 首页 | 一句话定位、找老师/找需求两个入口、联系流程简述 | 找老师、找需求 |
| 老师列表 | 紧凑筛选；方向、方式、区域、报价、可服务时间 | 查看老师 |
| 需求列表 | 紧凑筛选；目标、对象、方式、地点、预算、时间摘要 | 查看需求 |

| 我的联系（可作为“撮合进度”的候选名称） | 待我处理、等待对方、已互选；对象与需求关联 | 回应意向、交换联系方式 |
| 本人资料 | 资料维护、公开状态、私密联系方式 | 保存、预览并公开、管理联系方式 |

页面名称可调整，后台关系与权限不必随之改变。首页不需要展示未经授权的老师资料；已有登录账号也不必再次选择身份。

## 7. 推荐实施顺序与回归检查

### 第一轮：让核心路径连贯

1. P1-02/P1-03：登录返回目标、可恢复路由、筛选和返回位置。
2. P1-01：明确双入口与“联系”的实际流程。
3. P1-04/P1-05：压缩筛选区，补齐卡片决策信息。
4. P1-06/P1-07：改善意向/授权用语、待办入口和下一步位置。

### 第二轮：完善状态和一致性

修复加载中假空态，统一筛选重置、金额和详情分区；验证老师保存后的公开引导；同步过时文档。预算筛选、结构化方向等有数据和使用反馈后再加。

### 必须回归的场景

- 匿名老师浏览需求→登录→返回原详情；首次资料未完善、身份不符、需求到期分别验证。
- 需求方筛选老师→详情→选择本人需求；没有有效需求时清楚引导，完成前置步骤后能继续寻找原老师。
- 筛选→翻页→详情→返回、刷新、浏览器前进后退；老师私有详情不得因可复制 URL 绕过权限。
- 双账号覆盖发起、回应、双方授权、撤回、联系方式变更；体验简化不能改变隐私边界。
- 390×844 和桌面检查；增加键盘焦点、缩放和慢网检查。本轮没有完成真机、屏幕阅读器或完整无障碍验收。

实施后可记录浏览详情、发起意向、对方回应、双方完成授权等事件，观察从发现到联系的流失位置。两种角色分别分析；不记录联系方式明文，也不把“已互选”当作成交率。当前没有真实使用数据，因此不预设转化率改善百分比。

## 10. 用户反馈修正：直接邀请与联系方式保存（2026-11-11）

本节替代此前“邀请必须选择本人有效公开需求”的建议。用户明确两条独立路径：在老师广场直接邀请；或发布公开需求，等待老师投递。原实现将两条路径串联，尤其审核中的需求无法选择，形成不必要前置条件。

| 问题 | 修改 |
| --- | --- |
| 保存弹窗黑色、位置突兀 | 将浏览器原生确认改为页面内居中对话框，浅底深绿，支持 Escape、取消、焦点返回；保留必要的授权变更说明 |
| 未保存提示紧贴按钮 | 独立底部操作栏，状态在左、保存按钮在右；手机上下排列；未修改禁用保存 |
| 必须先发布审核需求才能邀请 | 增加直接邀请：只需选择老师，可选500字留言；无需求选择器、不创建隐藏需求、不自动分享联系方式 |
| 双向联系和历史进度 | 直接邀请与投递复用回应、逐项授权、撤回和变更重确认；已有进行中联系返回原记录；直接邀请被拒后阻止重复打扰，撤回重发使用新轮次 |

V6脚本：`backend/src/main/resources/db/migration/V6__direct_invitations.sql`。仅放开关系的request_id和轮次的submission_id非空限制，增加无需求关系的双方唯一索引及来源一致性触发器；不删除或更新既有数据，不修改V1—V5。邀请人展示名和可选留言作为本轮私有快照保存，老师与邀请人之外不可查看。

执行顺序：获准后先在`tuplatform_test`执行V6并运行合成数据库测试；通过后在`tuplatform`执行相同脚本，并重启本地8180应用使前后端一同生效。Flyway在事务中执行并记录版本；失败不手工跳过校验。不自动执行逆向DDL；应用回退前应先核实是否已有直接邀请数据。用户已明确批准两库V6迁移：专用测试库验证通过后，业务库已执行相同脚本并通过Flyway校验；8180已切换到新后端和前端。本地启动器同步允许已获准的V1—V6；未来新增迁移仍需单独确认。保留切换前JAR，不进行数据库逆向改写。

## 11. 撮合进度与联系流程简化（2026-11-11）

本节替代第9、10节中“互选后另行逐项授权”的交互建议。用户明确要求减少联系过程中的重复确认：发送邀请、投递和接受意向本身包含交换联系方式的同意，互选后直接联系。

| 用户反馈 | 当前改动 |
| --- | --- |
| 列表排版零散、卡片占用过大 | 对象名称、状态标签、下一步按钮组成紧凑卡片；待我回应优先；筛选改为直接切换，取消独立筛选表单和零待办大提示 |
| 详情文字过多、重点不明 | 顶部先展示联系对象和状态；待回应显示操作，互选显示联系方式；邀请留言保留，历史需求/老师资料默认折叠 |
| “读取最新进度”独占一行 | 改为标题旁的小型刷新入口；浏览器刷新仍可恢复当前详情 |
| 联系方式区重复说明、勾选和授权 | 发送/接受旁简短展示本人当前联系方式与说明；后台在同一事务记录同意，正常互选后直接显示对方手机号/微信 |
| 接受邀请出现深色原生弹窗 | 接受、婉拒、撤回统一使用浅底深绿页面弹窗，固定在可视窗口中央；支持取消、Escape和键盘焦点返回 |
| 管理规则挤占主流程 | 维护及停止分享折叠在“管理我的联系方式”，不再展示长篇轮询、远程清除等实现说明 |

兼容边界：旧记录此前没有同意自动交换，不回填授权，改为一个“同意交换联系方式”按钮；没有联系方式仍可先发意向，互选后补充。未填写时不授权未来新值。已分享字段变更、停止分享仍遵守原有有效性检查，旧回执不会恢复失效同意。新流程不再有额外的勾选、预览或授权表单。双方之外不能读取联系方式；邮箱始终不分享。

本次复用V5联系方式记录与V6直接邀请结构，无新增迁移、无数据库历史数据改写。所有邀请/接受/联系方式写入验收只使用专用测试库中的合成账号，不操作用户标注的真实联系记录。
